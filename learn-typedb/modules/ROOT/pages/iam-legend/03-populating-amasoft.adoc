== Why Does Insert Look Like This?

Before inserting anything, let's understand the pattern. Here is inserting Sam Rivera:

[,typeql]
----
insert
$sam isa fte,
  has name "Sam Rivera",
  has email "sam.rivera@amasoft.com",
  has employee-id "EMP-0042";
----

You might wonder: why do I need `$sam` at all? Why not just write 'insert fte, has name "Sam Rivera"'?

Compare with SQL:

[,sql]
----
-- SQL: a direct command
INSERT INTO employees (name, email, employee_id)
VALUES ('Sam Rivera', 'sam.rivera@amasoft.com', 'EMP-0042');
----

SQL says: go to this table, add a row, put these values in these columns. TypeQL works differently — it is a pattern language. You describe a pattern of what should exist, and TypeDB makes it so. The variable `$sam` is a handle you give to a slot in the pattern, so you can refer to it from multiple places in the same query.

For a simple insert this feels like ceremony. The power reveals itself the moment you insert something connected to something else:

[,sql]
----
-- SQL: look up IDs first, then insert
SELECT id INTO @sam_id FROM employees WHERE email = 'sam.rivera@amasoft.com';
SELECT id INTO @eng_id FROM departments WHERE name = 'Engineering';
INSERT INTO dept_membership (member_id, dept_id) VALUES (@sam_id, @eng_id);
----

[,typeql]
----
# TypeQL: describe the pattern in one query
match
$sam isa fte, has email "sam.rivera@amasoft.com";
$eng isa department, has dept-name "Engineering";
insert
(member: $sam, dept: $eng) isa dept-membership;
----

In the TypeQL version, `$sam` and `$eng` are the handles that connect the `match` clause to the `insert` clause. This is what pattern language means in practice.

[NOTE]
.💡 You can skip naming the variable if you don't need it
====
If you never refer back to the variable in the same query, use `$_` as a throwaway: `# Named — use when you need to reference it later` `insert $sam isa fte, has name "Sam Rivera";` `# Throwaway — fine for a standalone insert` `insert $_ isa fte, has name "Sam Rivera";` Both do exactly the same thing here.
====

[NOTE]
.⭐ TypeDB Advantage: One consistent pattern language for reads and writes
====
In SQL, reading uses `SELECT` with `JOIN` while writing uses `INSERT INTO` with `VALUES` — completely different syntax. In TypeQL, the pattern is the same everywhere: `match` describes what exists, `insert` describes what to add. Once you know how to write a match pattern, you already know the match part of every insert, delete, and update.
====

====

== Inserting Relations

[,typeql]
----
# Place Sam in Engineering
match
$sam isa fte, has email "sam.rivera@amasoft.com";
$eng isa department, has dept-name "Engineering";
insert
(member: $sam, dept: $eng) isa dept-membership;
# Place Alex in Engineering, reporting to Sam
match
$alex isa contractor, has email "alex.chen@amasoft.com";
$sam isa fte, has email "sam.rivera@amasoft.com";
$eng isa department, has dept-name "Engineering";
insert
(member: $alex, dept: $eng) isa dept-membership;
(manager: $sam, report: $alex) isa reports-to,
  has effective-from 2024-01-15T00:00:00;
----

[NOTE]
.💡 The match-insert pattern
====
The `match` clause finds existing instances. The `insert` clause uses those found instances to create something new. You cannot insert a relation without first finding its participants.
====

== Your First Fetch Queries

Who is in Engineering?

[NOTE]
.💡 Three rules for fetch
====
. CURLY BRACKETS — `fetch` uses `{ }` not `( )`.
. KEY-VALUE PAIRS — the key is a label you choose in double quotes.
. MATCH IS A FILTER — only instances that have the matched attributes appear.
====

[,typeql]
----
match
$p has name $name;
$d isa department, has dept-name "Engineering";
(member: $p, dept: $d) isa dept-membership;
fetch { "name": $name };
----

[TIP]
.🗺️ Switch to Table view for easier reading
====
By default Studio shows fetch results as JSON in the log panel. Look for the output format toggle in the results toolbar and switch it to Table — it presents results as rows and columns, which is much easier to read when you have multiple results.
====

Who reports to Sam?

[,typeql]
----
match
$sam has name "Sam Rivera";
$report has name $report_name;
(manager: $sam, report: $report) isa reports-to;
fetch { "report": $report_name };
----

== What Type Is Each Person? — Three Queries

This is one of TypeDB's most distinctive capabilities. In SQL, a row's type is implicit — it's whichever table the row lives in. In TypeDB, types are first-class data you can query, traverse, and reason about directly. Here are three versions of the same question, each revealing something different.

=== Query 1 — All types in the hierarchy (sub)

Using `sub` without `!` climbs the full hierarchy. A contractor appears multiple times — once for each type it belongs to:

[,typeql]
----
match
$p isa $type;
$type sub person;
$p has name $name;
fetch { "name": $name, "type": label($type) };
----

Alex Chen would appear four times: as `contractor`, `temporary`, `person`, and `identity`. Useful when you want the full classification chain — but often more than you need.

=== Query 2 — Direct subtypes only (sub!)

Adding `!` constrains the result to direct subtypes only — one level down from the specified type:

[,typeql]
----
match
$p isa $type;
$type sub! person;
$p has name $name;
fetch { "name": $name, "type": label($type) };
----

Now Alex appears once — as `contractor`, the direct subtype of `person` that applies. Sam appears as `fte`. Much cleaner, but still not necessarily the most specific type if the hierarchy goes deeper.

=== Query 3 — The most specific type (lowest in hierarchy)

This query finds the single most precise type for each person — the lowest node in the hierarchy they belong to:

[,typeql]
----
match
$p isa $type;
$p has name $name;
not { $other sub! $type; $p isa $other; };
fetch { "name": $name, "type": label($type) };
----

The `not` clause is the key: exclude any result where there exists a more specific subtype that `$p` also belongs to. What remains is only the most specific type — the bottom of the hierarchy for that instance.

[NOTE]
.💡 Reading the not clause
====
`not { $other sub! $type; $p isa $other; }` says: 'there does not exist a type `$other` that is a direct subtype of `$type`, where `$p` is also an instance of `$other`.' `$other` is not a keyword — it is just a variable name chosen to read naturally as 'some other more specific type'. You could call it `$child` or `$subtype` and the query would work identically. The result: Alex appears exactly once as `contractor`. Sam appears exactly once as `fte`. Every person appears at their most specific classification.
====

[NOTE]
.⭐ TypeDB Advantage: Types are first-class queryable data
====
In SQL, getting the most specific type of a row requires a discriminator column, application logic, or querying multiple tables. In a property graph database, node labels are stored but not traversable in a type hierarchy. In TypeDB, the entire type system is queryable. You can ask 'what is the most specific type of this identity?' in a single declarative query. The schema enforces the hierarchy; the query traverses it.
====

== Alex's First Promotion — contractor to fte

Alex's contract period is ending and they've been offered a full-time role. This is the right moment to record the transition — before access grants are added in Chapter Four. Right now Alex only has a `dept-membership` and a `reports-to` bond, making the process clean.

[WARNING]
.⚠️ Delete relations before deleting the identity
====
TypeDB's cardinality constraints protect data integrity during deletes as well as inserts. If a relation has `@card(0..)` or `@card(1..)` on a role, deleting the role player would leave the relation in an invalid state — TypeDB will reject the commit. Always delete dependent relations first, then delete the identity. Run each as a separate query:
====

[,typeql]
----
# Step 1: Delete dept-membership
match
$alex isa contractor, has email "alex.chen@amasoft.com";
$dm links (member: $alex), isa dept-membership;
delete $dm;
# Step 2: Delete reports-to bond
match
$alex isa contractor, has email "alex.chen@amasoft.com";
$rt links (report: $alex), isa reports-to;
delete $rt;
# Step 3: Delete the contractor record
match $alex isa contractor, has email "alex.chen@amasoft.com";
delete $alex;
# Step 4: Reinsert as fte
insert $_ isa fte,
  has name "Alex Chen",
  has email "alex.chen@amasoft.com",
  has employee-id "EMP-0099";
# Step 5: Recreate dept-membership and reports-to
match
$alex isa fte, has email "alex.chen@amasoft.com";
$eng isa department, has dept-name "Engineering";
$sam isa fte, has email "sam.rivera@amasoft.com";
insert
(member: $alex, dept: $eng) isa dept-membership;
(manager: $sam, report: $alex) isa reports-to,
  has effective-from 2024-07-01T00:00:00;
----

[NOTE]
.💡 Why this is a natural access review checkpoint
====
When Alex is deleted as a contractor, all their access grants are deleted too — they are relations that depend on Alex existing. After reinserting as an `fte`, access must be explicitly re-granted. This is correct behaviour: a type change is a natural moment to review what access the person should have in their new role.
====
