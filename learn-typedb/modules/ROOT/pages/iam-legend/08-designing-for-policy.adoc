== The Situation

Amasoft's IAM system is working. But the CISO has a new requirement: some access grants need conditions attached — time-of-day restrictions, approval requirements, or temporary exceptions granted by named individuals with expiry dates. How should this be modelled? This is Chapter Eight's central design debate.

== The Access Policy Design Debate

Three ways to model conditional access. Working through them will teach you more about TypeDB schema design than any single worked example.

=== Option A — Permission Level as an Attribute

What we already have: permission-level is an attribute on `access-grant`. Simple, but you lose the reason — was this a policy-based grant or a manual exception? And you cannot query 'who should have access' versus 'who does'.

=== Option B — Policy as a Function

Encode the access rule as a TypeQL function as we did in Chapter Seven. The function IS the policy — auditable, composable, callable from any query. But it lives in the schema, not the data. A function tells you who should have access right now based on current state. It cannot record why a specific grant was made, who approved it, or which policy was in effect at the time the grant was created. Functions answer 'should this person have access?' — they cannot answer 'under what policy was this access granted six months ago?'

=== Option C — Policy as a Relation (The Full Model)

[,typeql]
----
define
entity access-policy,
  owns policy-name @key,
  owns policy-description;
relation policy-grant,
  relates identity @card(0..1),
  relates policy @card(1),
  owns granted-by,
  owns granted-at,
  owns expires-at,
  owns reason;
relation policy-exception,
  relates identity @card(0..1),
  relates policy @card(1),
  owns approved-by,
  owns approved-at,
  owns expires-at,
  owns reason;
attribute policy-name, value string;
attribute policy-description, value string;
attribute granted-by, value string;
attribute approved-by, value string;
attribute approved-at, value datetime;
attribute expires-at, value datetime;
attribute reason, value string;
----

Now you can see not just who has access, but under which policy, who granted the exception, and when it expires. The difference between 'Alex has payments access' and 'Alex has payments access because the CISO granted a time-limited exception that expires Friday'.

[NOTE]
.🏢 The Golden Rule
====
If something in the real world can exist independently — an access policy, a project team, a department — make it an entity. If something only exists because of a connection between two things — a grant, a membership, a reporting line — make it a relation. If something is just a value — a permission level, a date, a name — make it an attribute.
====

[NOTE]
.⭐ TypeDB Advantage: Relations as first-class policy carriers
====
In SQL, storing the reason a grant was made, who approved it, and when it expires requires either additional columns on an access_grants table (making it very wide) or a separate exceptions table with foreign keys pointing at multiple other tables. In TypeDB, the `policy-grant` and `policy-exception` relations each own their attributes naturally — the reason lives on the bond, exactly where it belongs.
====

== Sub-relations: Specialising the Access Grant

Not all access grants are the same. A direct grant to an individual is different from a grant made under a formal policy, which is different from a temporary exception. These are all access grants — but specialised ones. Sub-relations capture this:

[,typeql]
----
define
relation direct-access sub access-grant;
relation policy-based-access sub access-grant,
  owns policy-name,
  owns approved-by;
relation temporary-exception sub access-grant,
  owns approved-by,
  owns expires-at,
  owns reason;
----

All three are `access-grant`s. Querying for `access-grant` returns all three automatically. But you can also query specifically for `temporary-exception`s that expire soon — or for `policy-based-access` where a specific person approved it.

[NOTE]
.💡 When to use a sub-relation
====
Use a sub-relation when two relation types are genuinely the same kind of thing — one is just a more specific version. A `temporary-exception` IS an `access-grant`, just with extra context and constraints. If the two connections feel fundamentally different rather than specialised, they should be separate relation types rather than a hierarchy.
====

[NOTE]
.⭐ TypeDB Advantage: Polymorphism applies to relations too
====
In SQL, there is no concept of a relation subtype. You would need separate tables for direct_access, policy_based_access, and temporary_exception — joined by a common foreign key — and your queries would need UNION ALL to treat them uniformly. In TypeDB, querying for `access-grant` automatically includes all subtypes. The hierarchy is enforced by the schema and resolved transparently at query time.
====

== Composition Over Inheritance

The level system taught this lesson already: Sam's promotion changed the level-assignment relation, not Sam's type. The same principle applies everywhere in the IAM schema.
