== The Situation

The compliance team keeps asking the same questions. The security team wants to know who *should* have access to payments, not just who does. And engineering has started a finance integration project — their engineers need temporary access to the payments system even though they're not in the finance department. All three problems have the same solution: functions.

== What Functions Actually Are

Before writing any code, consider what we're replacing. Here is Amasoft's payments access policy in SQL — the kind of query that lives in a stored procedure, or worse, duplicated across three different places in application code:

[,sql]
----
-- SQL: the payments access policy
-- This logic exists in the stored proc, the app code,
-- AND the compliance spreadsheet. They diverged 6 months ago.
SELECT u.name
FROM users u
JOIN user_levels ul ON u.id = ul.user_id
AND ul.effective_until IS NULL
JOIN levels l ON ul.level_id = l.id
JOIN dept_memberships dm ON u.id = dm.user_id
JOIN departments d ON dm.dept_id = d.id
AND d.name = 'Finance'
WHERE u.employment_type = 'fte'
AND l.level_number >= 5
UNION
SELECT u.name
FROM users u
JOIN user_levels ul ON u.id = ul.user_id
AND ul.effective_until IS NULL
JOIN levels l ON ul.level_id = l.id
WHERE l.level_number >= 7;
----

This query is correct today. But when the policy changes — when someone decides L4 Finance managers should also get access — you have to find every copy of this logic and update them all. And hope you didn't miss one.

[NOTE]
.🏢 The single source of truth problem
====
In most organisations, access policy lives in three places simultaneously: application code, a stored procedure, and a spreadsheet. They drift apart over time. Someone updates the app code and forgets the stored procedure. An auditor reads the spreadsheet and gets a different answer than the system enforces. In TypeDB, the function IS the policy. There is one place. There is no drift.
====

[,typeql]
----
define
fun can-access-payments($i: identity) -> { identity }:
  match
    { $i isa fte;
      $la links (identity: $i, level: $l), isa level-assignment;
      not { $la has effective-until $_; };
      $l has level-number $n; $n >= 5;
      (dept: $d, member: $i) isa dept-membership;
      $d isa department, has dept-name "Finance"; }
    or
    { $la links (identity: $i, level: $l), isa level-assignment;
      not { $la has effective-until $_; };
      $l has level-number $n; $n >= 7; };
  return { $i };
----

[WARNING]
.⚠️ Two syntax rules for functions
====
. Use `$_` (throwaway variable) in `not` clauses inside disjunction branches. A named variable like `$eu` used in two separate branches of an `or` will cause a 'locally-scoped variable' error — TypeDB requires variables to be either bound in a shared scope or anonymous.
. Use `isa` directly in disjunction branches when checking types — not `$type == type-name`. Type comparison with `==` is for value equality, not type checking.
====

Call it using the `let` keyword — required for all stream-returning function calls:

[,typeql]
----
match
  let $i in can-access-payments($i);
  $i has name $name;
fetch { "authorised": $name };
----

[NOTE]
.💡 The let keyword — two uses
====
In TypeDB 3.x, `let` has two distinct uses:

. Calling a stream-returning function: `let $i in can-access-payments($i);`
. Assigning a value expression: `let $source = "direct grant";`

For function calls, `let` is required — writing `$i in func()` without `let` is a syntax error.
====

[NOTE]
.💡 Functions as living policy documents
====
The TypeQL function IS the policy. It can be read by humans, called by applications, chained with other functions, and updated in one place when the policy changes. There is no stored procedure, no application code, no spreadsheet to keep in sync.
====

== Compliance Gap — Both Directions

The security team needs two reports: who should have access but doesn't (under-provisioned), and who has access but shouldn't (over-provisioned). Both start from the same policy function.

Under-provisioned — authorised but no grant. The logic is inlined rather than chained to avoid a known query planner limitation with zero-argument functions:

[,typeql]
----
define
fun missing-payments-access() -> { identity }:
  match
    $i isa identity;
    { $i isa fte;
      $la links (identity: $i, level: $l), isa level-assignment;
      not { $la has effective-until $_; };
      $l has level-number $n; $n >= 5;
      (dept: $d, member: $i) isa dept-membership;
      $d isa department, has dept-name "Finance"; }
    or
    { $la links (identity: $i, level: $l), isa level-assignment;
      not { $la has effective-until $_; };
      $l has level-number $n; $n >= 7; };
    not {
      $s isa payments-system;
      (grantee: $i, system: $s) isa access-grant;
    };
  return { $i };
----

Over-provisioned — has a grant but not authorised:

[,typeql]
----
define
fun unauthorised-payments-access() -> { identity }:
  match
    $i isa identity;
    $s isa payments-system;
    (grantee: $i, system: $s) isa access-grant;
    not { let $_ in can-access-payments($i); };
  return { $i };
----

[NOTE]
.💡 Updating an existing function
====
If you need to redefine a function that already exists, use `redefine`: `redefine fun unauthorised-payments-access() -> { identity }: ...` If the function doesn't exist yet, use `define`. If you get 'function already exists' on `define`, switch to `redefine`. If you get 'function not found' on `redefine`, switch to `define`.
====

Call both and act on the results:

[,typeql]
----
# Under-provisioned — Michelle should appear (L7, authorised but no grant)
match
  let $i in missing-payments-access();
  $i has name $name;
fetch { "needs-grant": $name };

# Over-provisioned — currently no results (no one has unauthorised access)
match
  let $i in unauthorised-payments-access();
  $i has name $name;
fetch { "revoke-access": $name };
----

The over-provisioned query returns nothing — which is correct. Nobody currently has payments access they shouldn't. Let's deliberately create an over-provisioning scenario to confirm the query works:

[,typeql]
----
# Grant Alex payments access — he's L2 in Engineering, not authorised
match
  $alex isa fte, has email "alex.chen@amasoft.com";
  $pay isa payments-system;
insert
  (grantee: $alex, system: $pay) isa access-grant,
    has permission-level "read",
    has granted-at 2024-08-01T09:00:00;

# Now run the over-provisioned query — Alex should appear
match
  let $i in unauthorised-payments-access();
  $i has name $name;
fetch { "revoke-access": $name };
----

[NOTE]
.🏢 This is exactly what compliance teams worry about
====
Access drift — someone gets access they shouldn't have, often through a one-off exception or a copy-paste error — is one of the most common IAM failures. Most organisations discover it during an audit, months later. With TypeDB, one query finds it instantly. The policy is defined once. The gap is visible on demand.
====

[NOTE]
.🏢 Why this is impossible in SQL
====
In SQL, 'who should have access but doesn't' requires the full policy logic as a subquery, negated against the grants table. That's the 30-line UNION query from earlier, wrapped in a NOT EXISTS. And 'who has access but shouldn't' is the inverse. In practice, most organisations don't run these checks at all because writing them is too painful. In TypeDB, it's one function call each.
====

[NOTE]
.⭐ TypeDB Advantage: Policy as reusable composable logic
====
In SQL, access policy logic lives in application code, stored procedures, or spreadsheets — duplicated, diverging, invisible to queries. In TypeDB, the function is defined once, callable from any query, and always the single source of truth. The compliance gap queries above are only possible because the policy is a first-class named thing that can be referenced, negated, and composed.
====

== Chaining Functions

Functions compose by calling them in the same match clause. Here is a two-function chain that finds contractors with sensitive system access whose contracts expire soon — the highest-priority access review list:

[,typeql]
----
define
fun contract-expiring-soon($i: identity) -> { identity }:
  match
    $i isa temporary, has contract-end-date $end;
    $end < 2024-08-01T00:00:00;
  return { $i };

fun has-sensitive-access($i: identity) -> { identity }:
  match
    { $s isa payments-system; }
    or { $s isa finance-platform; };
    (grantee: $i, system: $s) isa access-grant;
  return { $i };
----

Call both together in a single match clause:

[,typeql]
----
match
  let $i in contract-expiring-soon($i);
  let $i in has-sensitive-access($i);
  $i has name $name;
fetch { "urgent-review": $name };
----

[NOTE]
.💡 Function composition in TypeDB
====
Functions compose by calling them in sequence in the same match clause. Each `let $i in func($i)` statement further constrains the stream — only identities that satisfy all function calls are returned. This is the idiomatic TypeDB pattern for complex policy questions: define each policy as a simple named function, then compose them at query time. When a policy changes, update one function. Every query that uses it updates automatically.
====

[WARNING]
.⚠️ Zero-argument wrapper functions hit a known planner limitation
====
You might be tempted to wrap the chain in a named zero-argument function:

[,typeql]
----
fun urgent-access-review() -> { identity }:
  match
    let $i in contract-expiring-soon($i);
    let $i in has-sensitive-access($i);
  return { $i };
----

This defines correctly but the call query hits a TypeDB query planner bug — the planner cannot find a valid execution order when a zero-argument function chains other stream functions. The workaround is to call the component functions directly in the match clause, as shown above. This is a known TypeDB issue and likely to be fixed in a future release.
====

== Project Teams — A Second Path to Access

Engineering has started a finance integration project. The project engineers need access to the payments system — but they're not in Finance and they're not L5. Their access comes from project team membership, not their permanent role.

[,typeql]
----
define
entity project-team,
  owns team-name @key,
  owns project-code;
relation project-membership,
  relates team @card(1),
  relates member @card(0..),
  owns start-date,
  owns end-date;
relation project-access,
  relates team @card(1),
  relates system @card(1),
  owns permission-level;
entity identity, plays project-membership:member;
entity project-team,
  plays project-membership:team,
  plays project-access:team;
entity system, plays project-access:system;
attribute team-name, value string;
attribute project-code, value string;
attribute start-date, value datetime;
attribute end-date, value datetime;

insert $_ isa project-team,
  has team-name "Finance Integration",
  has project-code "FIN-2024";

match
  $t isa project-team, has team-name "Finance Integration";
  $s isa payments-system;
insert
  (team: $t, system: $s) isa project-access,
    has permission-level "read";

match
  $t isa project-team, has team-name "Finance Integration";
  $alex isa fte, has email "alex.chen@amasoft.com";
insert
  (team: $t, member: $alex) isa project-membership,
    has start-date 2024-07-15T00:00:00;
----

== Two Paths to the Same System

Now Alex has access to payments via two possible paths: direct access-grant, or project team membership. Query both at once with disjunction — and surface the source of access:

[,typeql]
----
match
  $i has name $name;
  $s isa payments-system;
  { (grantee: $i, system: $s) isa access-grant;
    let $source = "direct grant"; }
  or
  { (member: $i, team: $t) isa project-membership;
    (team: $t, system: $s) isa project-access;
    let $source = "project team"; };
fetch { "name": $name, "access-via": $source };
----

[NOTE]
.💡 let for value assignment
====
`let $source = "direct grant"` assigns a string literal to a variable within a disjunction branch. This is the second use of `let` — value expression assignment. The result includes the source label in the output, making it clear which path each identity's access came through.
====

[NOTE]
.⭐ TypeDB Advantage: Disjunctive path traversal
====
In SQL, finding identities with access via either a direct grant or project team membership requires UNION ALL across two completely different join chains — typically five or more tables, with duplicate elimination on top. In TypeQL, both access paths are expressed as a single disjunctive pattern. TypeDB resolves both paths, deduplicates automatically, and returns the source of access in the same query.
====

== Separation of Duties — The Compliance Flex

Separation of Duties (SoD) is one of the most important — and most notoriously difficult — compliance requirements to enforce. The rule: the person who can create a payment cannot be the same person who can approve it. In SQL, enforcing SoD requires complex joins across multiple permission tables. In TypeDB, it's one function:

[,typeql]
----
define
fun sod-violation() -> { identity }:
  match
    $i isa identity, has account-status "active";
    $pay isa payments-system;
    $hr isa hr-system;
    (grantee: $i, system: $pay) isa access-grant,
      has permission-level "write";
    (grantee: $i, system: $hr) isa access-grant,
      has permission-level "admin";
  return { $i };

match
  let $i in sod-violation();
  $i has name $name;
fetch { "sod-violation": $name };
----

[NOTE]
.⭐ TypeDB Advantage: Separation of Duties as a first-class query
====
In SQL, enforcing SoD requires joining across multiple permission tables, checking multiple conditions, and usually duplicating the logic across application code and stored procedures. In TypeDB, SoD is a function — defined once, called anywhere, always consistent. When the rule changes, you update one function. The audit query and the enforcement logic are the same code.
====
