== Previously

In Chapter One you defined staff with email `@key` and an abstract department with name `@key`. Chapter Two builds the full identity hierarchy on top of these foundations — purely additive, no migration needed. It also puts one Chapter One decision under the microscope: whether departments deserve subtypes at all.

== The First Subtypes — Temporary Staff

Chapter One's staff type covers anyone who works at Amasoft. But contractors and interns carry information the rest of the staff won't: a contract end date. That calls for subtypes. Conceptually, both fit under the umbrella term of "temporary staff", so we introduce a shared parent for the pair — and while we're at it, every staff member deserves a name:

[,typeql]
----
define
attribute contract-end-date, value date;
entity staff,
  owns name;
entity temporary-staff sub staff,
  owns contract-end-date;
entity contractor sub temporary-staff;
entity intern sub temporary-staff;
----

contractor and intern inherit `name` and `email` from `staff`, plus `contract-end-date` from `temporary-staff` — an attribute that earns its keep in Chapter Seven, when a policy function warns about expiring contracts. Notice that this define also touched the existing staff type: running define on a type that already exists adds to it, so `owns name` slots in alongside Chapter One's email `@key` — no migration needed. And notice what is _not_ declared: the name attribute already exists — department has owned it since Chapter One — so staff simply takes ownership of the same attribute type.

Now make both parent types abstract — a bare staff member or a bare 'temporary staff member' is never what we want, only a specific kind:

[,typeql]
----
define
entity staff @abstract;
entity temporary-staff @abstract;
----

This in-place schema modification succeeds because neither type has instances yet. You will now no longer be able to insert a bare staff or temporary-staff — only a concrete subtype. staff is abstract for the same reason department is — we never want a bare instance.

Note: an abstract type must have an abstract supertype — TypeDB will reject `@abstract` on a type whose parent is concrete. Making temporary-staff abstract on its own would fail this rule; it works here because staff becomes abstract in the same query, and TypeDB validates the schema that results from the define as a whole.

[NOTE.yellow]
.💡 Inheritance is automatic
====
When you query for all 'staff' instances, TypeDB automatically includes contractors, interns, and every other staff subtype you define. The hierarchy is active at query time with no extra work.
====

[NOTE.blue]
.⭐ TypeDB Advantage: Polymorphic queries across a hierarchy
====
In SQL, querying across a type hierarchy requires UNION ALL across multiple tables, or a discriminator column with complex JOIN logic. In TypeDB, the hierarchy is declared once and resolved automatically. Querying for 'staff' includes all subtypes — guaranteed correct because the schema validates it.
====

== Permanent Staff — Full-time and Part-time

The rest of Amasoft's staff are salaried. Let's add a subtype branch for them:

[,typeql]
----
define
entity permanent-staff @abstract, sub staff;
entity full-time-employee sub permanent-staff;
entity part-time-employee sub permanent-staff;
----

The two leaves inherit everything from `permanent-staff`, and hence also from `staff`. Notice that permanent-staff declares no attributes of its own — its value is structural. It names the salaried half of the hierarchy and carries the full-time/part-time split.

== Service Accounts — Beyond Humans

RBAC is not just about people. Every API integration, every bot needs access managed too. Introduce a shared abstract root and a non-human identity type:

[,typeql]
----
define
entity identity @abstract,
  owns identity-status;
entity staff sub identity;
entity service-account sub identity,
  owns name,
  owns service-name @key,
  owns owner-team;
attribute service-name, value string;
attribute owner-team, value string;
attribute identity-status, value string
  @values("active", "suspended", "terminated");
----

Notice that `identity @abstract` now owns `identity-status` - a global kill switch. Suspended and terminated identities stay in the database with their history intact, but they must fail every access check - you will build that check in Chapter Nine. Both humans and service accounts need this. `@values` restricts it to exactly three valid states at the schema level.

There is a second, quieter lesson in this block: `entity staff sub identity;` gives staff — a type that has existed since Chapter One — a new parent, in place. TypeDB allows you to modify type hierarchies like this at any time, provided the change would not introduce conflicts. No migration scripts.

A word on the attributes. name is not new — it is the same globally scoped attribute type department and staff already own, and giving service accounts a display name means any audit that lists identities by name includes the machines automatically. service-name is the account's unique identifier — the machine analogue of email, which is why it carries `@key`. And owner-team records which team is accountable for the account — when a bot misbehaves or its access comes up for review, that is who you call. Chapter Six will use all three.

[NOTE.blue]
.⭐ TypeDB Advantage: Service accounts are first-class identities
====
SQL-based IAM systems typically bolt service accounts on as an afterthought — a separate table with a foreign key back to the user table. In TypeDB, service-account is a subtype of identity. It participates in the same access model as humans — same relations, same queries, same policies.
====

== The System Hierarchy

Now we add the systems that identities will be granted access to. Systems form a genuine hierarchy: an abstract system type with a concrete subtype per platform. The subtypes earn their place in the schema because access policies will refer to them by name — as when Chapter Seven's separation-of-duties function distinguishes payments-system from hr-system:

[,typeql]
----
define
entity system @abstract,
  owns system-name @key,
  owns description;
entity payments-system sub system;
entity hr-system sub system;
entity engineering-platform sub system;
entity finance-platform sub system;
attribute system-name, value string;
attribute description, value string;
----

== Departments Revisited — Types or Data?

Chapter One marked department `@abstract`, planning a concrete subtype per department — engineering, finance, hr-dept, legal — mirroring the system hierarchy above. Put the two side by side, though, and the plan falls apart. System subtypes are referenced by the schema itself: policies and queries will name payments-system directly. Department subtypes would be referenced by nothing — no policy will ever name legal — and every new department would cost a schema change. Departments are labelled instances of one concept: they are data, not types.

TypeDB lets us walk the decision back in place. This is `undefine` from the table earlier in this chapter, doing its first real work in this guide:

[,typeql]
----
undefine
@abstract from department;
----

department keeps its definition and its name `@key` — only the annotation is removed. Because no department instances exist yet, nothing else is affected. department is now a single concrete type, and the individual departments — Engineering, Finance, HR, Legal — will be inserted as plain data in Chapter Three.

[NOTE.yellow]
.💡 Departments are data, not types
====
The rule of thumb this correction teaches: make something a type when the schema itself must refer to it — in policies, functions, or role constraints. Make it data when the instances are interchangeable labels that no query will ever name individually. Adding a system is a schema change, and should be. Adding a department is just an insert query.
====

[NOTE.yellow]
.⚠️ If you see 'type department was not found'
====
This means department wasn't defined in Chapter One. Run: `define attribute name, value string; entity department, owns name @key;` — this defines it as concrete directly, so skip the undefine step above and continue.
====

Check the schema visualiser now. You have just built three separate groups of types:

* The system hierarchy — system, payments-system, hr-system, engineering-platform, finance-platform

In the visualiser you will see three completely separate graphs. Nothing connects them. There are no edges between the islands. This is correct — we have defined what exists, but not yet how things relate to each other.

[NOTE.yellow]
.🗺️ Three islands — about to be connected
====
This is one of the most important moments in schema design: seeing the structure before the connections. Each island is a complete hierarchy on its own. Relations are the bridges between them. Every relation you define in the next section will add an edge that connects two previously isolated groups.
====

== What is a Relation?

A relation is TypeDB's way of recording a connection between two or more things. Unlike a foreign key in SQL — which is just a number stored in a column — a TypeDB relation is a first-class entity in its own right. It can own attributes, participate in other relations, and be queried like any other type.

Every relation has named roles. Roles are the slots that participants fill.

== Relations — The Reporting Line

The first bridge: who reports to whom. In Amasoft, only permanent employees can manage people — contractors and interns report upward but never manage others. We encode this policy directly in the schema:

[,typeql]
----
define
attribute start-date, value date;
relation reports-to,
  relates manager @card(0..1),
  relates report @card(0..),
  owns start-date;
entity permanent-staff, plays reports-to:manager;
entity staff, plays reports-to:report;
----

When you define a relation, you choose the role names yourself. You choose role names based on the function a participant plays in the relationship, not their entity type. The reporting line relation has roles called 'manager' and 'report' (not 'staff' and 'staff').

Relations are not just connections — they are first-class types that can own attributes. The date this reporting line became effective lives on the bond itself, not in a separate table. This means you can query it directly, without a JOIN.

`@card(0..1)` on manager means at most one manager per bond. `@card(0..)` on report means zero or more reports — we use `0..` rather than `1..` to allow clean deletion of a report without the relation complaining.

[NOTE.yellow]
.⚠️ Role names are not entity type names
====
When you insert a relation, you always use the role name: `$reports_to isa reports-to, links (manager: $sam, report: $alex);` The error 'Role label not found' means you used the wrong name. When you see it, go back to the `relates` declaration and check what the role is actually called.
====

[NOTE.yellow]
.💡 Inheritance does the work here
====
Notice that manager is granted to permanent-staff, but report is granted to staff — the parent type. Because contractor and intern are subtypes of staff, they automatically inherit the ability to play the report role. No additional `plays` declarations needed. Because only permanent-staff can play manager, TypeDB will reject any insert that tries to make a contractor or intern a manager. The business rule is structural — enforced by the schema, not application code. This is one of the most powerful aspects of TypeDB's type hierarchy: you get precise, inheritance-aware role control in two lines.
====

[NOTE.blue]
.⭐ TypeDB Advantage: Relations own attributes natively
====
In SQL, storing when a reporting relationship became effective requires a separate junction table with its own columns. In TypeDB, start-date lives on the bond itself — semantically correct and queryable without a JOIN.
====

.🗺️ Check the schema visualiser
====
After running this define, check the schema visualiser. You will now see edges connecting identity nodes to each other through reports-to. One of the three islands has grown internal connections.
====

== Department Membership

The second bridge: which department each staff member belongs to:

[,typeql]
----
define
relation dept-membership,
  relates dept @card(1),
  relates member @card(0..);
entity department, plays dept-membership:dept;
entity staff, plays dept-membership:member;
----

[NOTE.yellow]
.💡 @card(1) on dept
====
`@card(1)` on the dept role means each individual dept-membership bond must reference exactly one department. It does not mean there can only be one department in the database.
====

[NOTE.yellow]
.🗺️ Check the schema visualiser
====
After running this define, look again. You will now see edges connecting the identity island to the department island. Two of the three islands are now connected.
====

.🗺️ Check the Schema Visualiser now
====
Go to the Schema page in TypeDB Studio — it reflects your schema automatically. You should see all entity types as nodes connected by their inheritance hierarchy, with reports-to and dept-membership as relation edges. If anything looks wrong, fix it now — before you insert any data.
====

[NOTE.yellow]
.💡 Natural extensions — what we deliberately left out
====
This schema is intentionally simple for demonstration. In a real IAM deployment you might also consider: • Sub-departments — Engineering might have sub-teams like Platform, Product, and Security, each with their own access profiles. • Regional or office-specific access — identities in the EU region may have different access to certain systems than those in APAC, due to data residency requirements. • System ownership — a department could formally own a set of systems. Finance owns payments and finance-core; Engineering owns eng-platform. This would let you query 'who has access to systems outside their department's ownership?' — a powerful audit query. All of these are straightforward to add in TypeDB. For now, we keep the structure simple so the core concepts stay clear.
====
