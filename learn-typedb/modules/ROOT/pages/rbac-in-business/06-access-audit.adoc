== Comparison Operators

Comparison operators filter results by value. They go in the match clause, on a separate line after binding the variable:

[,typeql]
----
# All identities at L5 or above
match
$i has name $name;
$la links (identity: $i, level: $l), isa level-assignment;
not { $la has effective-until $_; };
$l has level-number $n;
$n >= 5;
fetch { "name": $name, "level": $n };
----

[NOTE.yellow]
.💡 This query may return no results — that's expected
====
This query only returns results if you have access grants with a valid-until date set. If you completed the bonus in Chapter Four's challenge, you will have one. If not, add a valid-until date to one of your existing grants first: `match $i has email "alex.chen@amasoft.com"; $s isa engineering-platform; $ag (grantee: $i, system: $s) isa access-grant; update $ag has valid-until 2024-02-10T00:00:00;`
====

[,typeql]
----
# Access grants expiring before a specific date
match
$i has name $name;
$s has system-name $sys;
$ag (grantee: $i, system: $s) isa access-grant,
  has valid-until $vu;
$vu < 2024-02-15T00:00:00;
fetch { "identity": $name, "system": $sys, "expires": $vu };
----

== Who Has Admin Access?

[,typeql]
----
match
$i has name $name;
$s has system-name $sys;
(grantee: $i, system: $s) isa access-grant,
  has permission-level "admin";
fetch { "name": $name, "system": $sys };
----

== An Audit Finding — the Over-Privileged Bot

The admin query returns two rows: Sam Rivera — expected — and CI Deploy Bot. That second row is a problem. A deployment bot needs to push artifacts: write access. Nobody reviewed the grant, and it went in as admin.

This is exactly what access audits exist to catch. And notice that the query needed nothing special to catch it: the bot has a name like every other identity, so the same sweep that audits the humans audits the machines. No second query, no bot-shaped exception — if your audit needs a special case for service accounts, that is a modelling smell, not a querying fact of life.

Who answers for the finding? That is what owner-team is for:

[,typeql]
----
match
$sa isa service-account, has name "CI Deploy Bot",
  has service-name $sn, has owner-team $team;
$s has system-name $sys;
(grantee: $sa, system: $s) isa access-grant,
  has permission-level $pl;
fetch { "service-account": $sn, "owner-team": $team, "system": $sys, "permission": $pl };
----

One row: ci-deploy-bot, owned by Engineering, admin on the engineering platform. The finding lands on Engineering's desk with a note from Michelle Rocksmasher — running this audit is precisely why Chapter Four gave the CISO read access across every system: your bot has excess credentials, and it just failed our audit. The fix — revoking the admin grant without destroying its history — is a job for Chapter Nine.

== Which Temporary Workers Have Write or Admin Access?

[NOTE.yellow]
.💡 This query may return no results — that's expected
====
Alex was promoted from contractor to full-time employee in Chapter Three. Unless you inserted additional contractors or interns and granted them write or admin access, this query will return no results. That is correct — it means Amasoft currently has no temporary workers with elevated access, which is a good sign. To test the query, insert a new contractor and grant them write access, then run it again.
====

[,typeql]
----
match
$i isa temporary-worker, has name $name;
$s has system-name $sys;
(grantee: $i, system: $s) isa access-grant,
  has permission-level $pl;
{ $pl == "write"; } or { $pl == "admin"; };
fetch { "name": $name, "system": $sys, "permission": $pl };
----

[NOTE.yellow]
.💡 Disjunction — OR conditions
====
The `{ ... } or { ... }` pattern means either condition can be true. TypeDB returns results matching either branch. This is cleaner than SQL's `WHERE pl IN ('write', 'admin')` and works naturally with complex multi-line conditions.
====

== What Type of Identity Has Access to Payments?

The compliance team wants to know not just who has access to the payments system, but what kind of identity each person is:

[,typeql]
----
match
$i isa $type;
$type sub identity;
not { $other sub! $type; $i isa $other; };
$s isa payments-system;
(grantee: $i, system: $s) isa access-grant;
$i has name $name;
fetch { "name": $name, "identity-type": label($type) };
----

The negation keeps only each grantee's most specific type — contractor, intern, full-time-employee, and so on. It is the same pattern you used in Chapter Three: without it, `$i isa $type` would match every level of the hierarchy at once, and a contractor would appear as contractor, temporary-worker, worker, and identity. `label($type)` extracts the string name of the type.

[NOTE.blue]
.⭐ TypeDB Advantage: Types are first-class queryable data
====
In SQL, a row's type is implicit — it's whichever table the row lives in. Getting 'what kind of identity is this?' requires a JOIN back to a type lookup table, or a discriminator column. In TypeDB, types are fully first-class. You can bind them to variables, filter with `sub` and `sub!`, and return their labels as values in a `fetch`.
====

== Aggregation — The Numbers

Count access grants by permission level:

[,typeql]
----
match
$ag isa access-grant, has permission-level $pl;
reduce $count = count($ag) groupby $pl;
fetch { "permission": $pl, "count": $count };
----

Average level across all employees, grouped by department:

[,typeql]
----
match
$e isa permanent-worker, has name $name;
$d isa department, has dept-name $dept;
(dept: $d, member: $e) isa dept-membership;
$la links (identity: $e, level: $l), isa level-assignment;
not { $la has effective-until $_; };
$l has level-number $n;
reduce $avg = mean($n) groupby $dept;
fetch { "department": $dept, "avg-level": $avg };
----

[NOTE.yellow]
.💡 A query this schema can't answer yet — and how to fix it
====
A natural compliance question is: 'who has access to systems outside their department's ownership?' For example, does anyone in Engineering have admin access to the payments system, which Finance owns? This query isn't possible with the current schema because systems and departments aren't connected. A system-ownership relation would fix it: `relation system-ownership, relates dept, relates system;` With that defined, you could query for identities whose department has no ownership over the systems they can access — a powerful cross-department access audit. We left this out to keep the schema simple, but it's a natural next step in a real deployment.
====

== Pipeline Ordering — sort, limit, fetch

Find the top 5 most privileged identities by number of admin access grants:

[,typeql]
----
match
$i has name $name;
$ag (grantee: $i) isa access-grant,
  has permission-level "admin";
reduce $count = count($ag) groupby $name;
sort $count desc;
limit 5;
fetch { "name": $name, "admin-grants": $count };
----

[NOTE.yellow]
.⚠️ fetch must always be last
====
`fetch` is a terminal clause. The correct order is: `match` → `reduce` → `sort` → `limit` → `fetch`. BROKEN: `... fetch { ... }; limit 5;` CORRECT: `... limit 5; fetch { ... };`
====

== Debugging Queries That Return Nothing

When a query returns nothing unexpectedly, work from broad to narrow:

. Remove all filters — does any data come back?
. Add conditions one at a time until results disappear — that last condition is the problem.
. Check: wrong type (matched 'permanent-worker' but instance is 'intern'), wrong role name, case mismatch, pipeline order.
