=== Multi-server setup

TypeDB Enterprise can run as a single server, but a highly available, fault-tolerant production setup is a *cluster* of several servers that replicate the data between them.
At any point in time, one server is the primary and the others are secondaries; see xref:{page-version}@reference::typedb-cluster/index.adoc[Clustered TypeDB] for how a cluster works.
To tolerate `N` servers failing, a cluster needs `2N + 1` servers.
This section sets up a 3-server cluster, which tolerates the failure of one server.

Each server in a cluster binds to three network ports:
a gRPC port for TypeDB drivers and Console (`1729` by default), an HTTP port for the HTTP API and Studio (`8000`), and a clustering port for server-to-server replication (`1730`).
It also serves its xref:{page-version}@maintenance-operation::diagnostics-endpoint.adoc[monitoring endpoint] on port `4104`.

For this tutorial, all three servers are on the same private network with these ports open, and have the IP addresses `10.0.0.1`, `10.0.0.2`, and `10.0.0.3`.

[NOTE]
====
To try a cluster on a single machine, use `127.0.0.1` for every address and prefix each port with the server number:

* `11729`, `18000`, `11730`, `14104` for server 1;
* `21729`, `28000`, `21730`, `24104` for server 2;
* `31729`, `38000`, `31730`, `34104` for server 3.

Set these ports in each server's listen addresses (`--server.listen-address`, `--server.http.listen-address`), advertise addresses, clustering address, and `--diagnostics.monitoring.port`.
Run each server from its own copy of the distribution, or also give each one its own `--storage.data-directory`, `--storage.clustering-directory`, `--logging.directory`, and `--server.admin.socket-path`.
====

=== Starting the servers

Every server needs a unique replica id (`server.clustering.id`), its clustering address (`server.clustering.address`, which it also listens on for replication), the cluster's deployment id (`diagnostics.deployment-id`), and the addresses that clients should use to reach it (`server.advertise-address` and `server.http.advertise-address`).
The shipped `server/config.yml` holds localhost placeholders for these; set them in the file or pass them as command-line arguments, which take priority over the config file. See xref:{page-version}@maintenance-operation::typedb-configuration.adoc#_clustering[Cluster configuration].

.Server #1
====
On the machine with the IP address `10.0.0.1`, start the first server with `--initialize.create-cluster=true`.
This flag lets replica `1` create a new cluster on its first start; later starts ignore it.

[source,bash]
----
./typedb server \
    --diagnostics.deployment-id=my-cluster \
    --server.clustering.id=1 \
    --server.clustering.address=10.0.0.1:1730 \
    --server.advertise-address=10.0.0.1:1729 \
    --server.http.advertise-address=http://10.0.0.1:8000 \
    --server.admin.enabled=true \
    --initialize.create-cluster=true
----

The server prints `Ready to process requests` and already serves clients as a cluster of one.
====

.Servers #2 and #3
====
On `10.0.0.2`, start the second server without the `--initialize.create-cluster` flag:

[source,bash]
----
./typedb server \
    --diagnostics.deployment-id=my-cluster \
    --server.clustering.id=2 \
    --server.clustering.address=10.0.0.2:1730 \
    --server.advertise-address=10.0.0.2:1729 \
    --server.http.advertise-address=http://10.0.0.2:8000 \
    --server.admin.enabled=true
----

Start the third server on `10.0.0.3` the same way with `--server.clustering.id=3` and its own addresses.
Both servers wait to be registered.
====

=== Registering the servers

On the machine of server #1 (the primary), register the two new servers with the xref:{page-version}@tools::admin.adoc[admin tool], giving each one's replica id and clustering address:

[source,bash]
----
./typedb admin --socket-path ./server/data/admin.sock \
    --command "servers register 2 10.0.0.2:1730" \
    --command "servers register 3 10.0.0.3:1730"
----

Each new server receives the data from the primary and becomes a voting secondary once it has caught up.
Once they have caught up, check the result:

[source,bash]
----
./typedb admin --socket-path ./server/data/admin.sock --command "servers status"
----

[source]
----
id | address       | role      | term | status
-------------------------------------------------
1  | 10.0.0.1:1729 | primary   | 1    | available
2  | 10.0.0.2:1729 | secondary | 1    | available
3  | 10.0.0.3:1729 | secondary | 1    | available
----

The cluster is ready.
Connect with xref:{page-version}@tools::console.adoc[TypeDB Console] or a xref:{page-version}@reference::typedb-cluster/drivers.adoc[TypeDB driver] to any of the three addresses; requests are routed to the primary automatically.
See xref:{page-version}@reference::typedb-cluster/administration.adoc[Administering a cluster] for adding and removing servers later, failover, and migrating an existing TypeDB CE server into a cluster.

.Clients on a different network
====
Clients connect to every server at its advertise address, not only at the address they were given.
When clients reach the servers through addresses other than the ones the servers use among themselves (for example, public hostnames in front of a private network), set the advertise addresses to the client-facing ones and keep the clustering addresses private:

[source,bash]
----
./typedb server \
    --diagnostics.deployment-id=my-cluster \
    --server.clustering.id=1 \
    --server.clustering.address=10.0.0.1:1730 \
    --server.advertise-address=typedb-1.example.com:1729 \
    --server.http.advertise-address=http://typedb-1.example.com:8000 \
    --server.admin.enabled=true \
    --initialize.create-cluster=true
----

In this case, ports `1729` and `8000` need to be reachable by clients at the advertised hostnames, while port `1730` only needs to be open between the servers.
If no single address per server works for all clients, keep the advertise addresses private and let clients use address translation instead; see xref:{page-version}@reference::typedb-cluster/index.adoc#_client_addresses[How clients reach the replicas].
With xref:{page-version}@maintenance-operation::typedb-in-flight-encryption.adoc[TLS] enabled, the HTTP advertise address uses `https://`.
====

=== Stopping servers

Stopping a clustered server is done the same way as a single server: close the terminal or press kbd:[Ctrl+C].
Each server is shut down independently.
As long as a majority of the servers is running, the cluster keeps serving.
